# DNP3 매핑 MCU 비용과 독립 피어 검증

이 문서는 Outstation 게시 매핑 결과입니다.
Master 수신 매핑의 독립 피어·MCU·8/32/128 Point 비용은
[Master 하드웨어 샘플](../../../Samples/DNP3/VagabondK.nF.DNP3.MasterMapping/README.md)을 참조하십시오.

`Build\Test-Dnp3MappingHardware.ps1 -AllowDeviceChanges`로 실행합니다.
원본 OpenDNP3 Master, 복원 이미지 SHA256, COM3를 먼저 확인하고,
PC 회귀·샘플 및 여섯 계측 이미지를 모두 빌드한 뒤 장치를 변경합니다.
`finally`에서 원래 Modbus 앱을 복원하고 COM6 읽기를 검사합니다.
배포 실패는 로그를 남기고 최대 3회, 복원은 실패를 명시하고 한 번 재시도합니다.

## 측정 계약

- Analog Point 8/32/128개와 이벤트 용량 16/128개를 **독립적인 여섯 조합**으로 측정합니다.
  Static Variation 6, Event Variation 8을 사용하며 기존 최대 Point 512개 계약은 변경하지 않습니다.
- 모델 생성 전후, 바인딩·Database 생성 후의 GC 가용 힙을 기록합니다.
  잠금 객체·Point 정의·현재값·이벤트 기준·고정 이벤트 배열을 포함하며
  생성 중 해제되는 입력 정의 배열과 PE/네트워크/Station 비용은 별개입니다.
- 변경 없는 전체 Publish 100회 시간을 측정합니다. MCU TickCount64 해상도는 약 10ms입니다.
  값 변경·이벤트 초과·네트워크 시간과 혼동하지 않습니다.
- 선택 게시 추가 이후에는 첫/마지막 인덱스 선택 게시를 각각 1,000회 측정합니다.
  잠금·정수 누적, 모델 값·시각 읽기, `Dnp3Value.Analog` 생성,
  사전 생성한 값의 `Database.Update`(마지막 인덱스), 정수 누적 루프도 각각 1,000회 기록합니다.
  서로 독립된 마이크로벤치마크이며, 포함된 공통 루프·검사 비용이나 분기 차이가 있으므로
  단순 차감으로 검색/검증/Lock의 정확한 단독 비용을 주장하지 않습니다.
- TCP 20000의 독립 원본 OpenDNP3 Master가 Group 41 명령으로 전체 모델을 변경합니다.
  한 명령당 Publish는 한 번만 하며, 샘플의 반복 게시와 달리 의도적으로 누락 이벤트를 재시도하지 않습니다.
- 명령 후 모든 Static 값, 수용된 이벤트의 순서/인덱스·값·시각을 확인합니다.
  용량보다 Point가 많으면 Publish 실패·Overflow와 Static 갱신을 확인합니다.
  Master Confirmation으로 이벤트를 모두 제거한 후에만 Overflow를 해제합니다.
- 3회 준비 순회, GC 준비 후 100회 전체 순회(기본값)를 수행합니다.
  기준 및 매 10회 GC 표본에서 잔류 증가 0 B를 요구합니다.
- 전체 순회 뒤 첫/중간/마지막 Point의 선택 로컬 게시, Flags만 변경, Timestamp만 변경,
  Deadband와 같은 변화량 및 초과 변화량을 별도로 확인합니다.
  독립 Master가 모든 Static 값·Flags의 격리, 이벤트 개수·값·시각과 Confirmation 후 제거를 검사합니다.
  Timestamp만 변경하거나 정확히 Deadband만큼 변경하면 이벤트가 없어야 합니다.
  이 추가 검사는 100회 전체 순회의 GC 표본 구간과 구분합니다.
- 별도 UDP 20001 진단 채널은 `DNM1` + 명령(0 조회/1 GC/2 Overflow 해제/3~9 선택 게시 검사)입니다.
  `Program.cs`의 고정 100바이트 응답(기존 16개+비용 분해 8개 UInt32),
  GC 카운터, 디버거 미연결 여부 및 성공 식별값을 검사합니다.
  진단 패킷 처리 지역변수의 수명이 끝난 뒤 GC를 수행합니다.
- PE·배포 이미지 크기는 **시험/계측 코드 포함**입니다. 명령/Read 시간은 독립 피어의
  요청 완료 시간이며 전체 Point 응답과 Application Fragment Confirmation을 포함합니다.
  직접 제어와 Select+Operate는 각각 별도로 집계하며 전체 Control 집계는 두 경로의 혼합입니다.
  제어 응답은 모델 변경 후 반환되며 다음 루프의 Publish나 물리 장치 완료를 보장하지 않습니다.
  이어지는 Read 시간에는 그 게시 대기가 포함될 수 있습니다.
  작은 단일 Point RTT나 보장된 실시간 지연이 아닙니다.
- 준비 후 힙 잔류량은 최대 사용량, 스택, 네이티브 RAM, Wi-Fi RAM 또는 전체 할당량이 아닙니다.
  PC에서는 Publish의 무변경·이벤트 생성·초과 경로의 추가 관리 메모리 할당도 별도로 검사합니다.
  DNP3 프로토콜 처리 자체는 배열 할당이 있으며 전체 통신 무할당을 주장하지 않습니다.

출력 폴더에는 `sizes.csv`, 각 조합의 `measurements.json`, 배포/피어/복원 로그가 보존됩니다.

제어 성능 개선으로 해석하지 않습니다. 128개 전체 Publish 한 번은 이 조건에서 약 116.7ms여서
고주기 제어의 보장 지연으로 사용할 수 없습니다.

PC의 무변경·이벤트 생성·초과 게시도 추가 관리 메모리 할당이 0 B입니다.
기존 Database의 고정 이벤트/기준값 저장을 유지하는 설계이며,
새 캐시를 추가하거나 프로토콜 런타임의 이벤트 의미를 바꾸는 최적화는 하지 않았습니다.
수시간 반복 시험·물리 전원 차단·모든 네트워크 상황의 장기 안정성을 보장하는 결과는 아닙니다.

## 선택 게시와 내부 경로 최적화

`bin\dnp3-mapping-selective-first`는 선택 API와 비용 분해 계측만 추가한 대조군입니다.
위 최초 결과와 전체 게시 시간·모델·바인딩 RAM이 같은 수준임을 확인했습니다.
`bin\dnp3-mapping-optimized-final`은 같은 계측 코드에 다음 내부 최적화를 적용한 결과입니다.

- `Publish(type, index)`는 생성된 종류/인덱스 분기에서 해당 멤버만 읽습니다.
  실제 TCP 샘플도 변경 가능한 두 Status만 게시하며, 원본 OpenDNP3로 명령 후
  Static 값과 이벤트 품질·시각·Confirmation을 확인합니다.
- Point 값 검증은 종류별 switch로 분기하고 Analog 비트→Double 변환을 한 번만 수행합니다.
  이진 검색은 각 후보 정의의 Type/Index를 지역변수로 한 번씩 읽습니다.
  값 검증·검색·Database Lock을 생략하거나 새 공개 런타임 API를 추가하지 않습니다.
- 이전 값 캐시나 변경 감지로 `Update`를 생략하지 않습니다. 선택 게시도 기존 Update의
  이벤트 기준을 사용하므로 Overflow에서 누락된 이벤트를 같은 값으로 재시도할 수 있습니다.
  PC에서 이 재시도와 7종 Point, 희소 인덱스, 비대상 getter 미실행,
  공유 잠금 안에서의 스냅샷 읽기 및 잘못된 값·시각·대상 거부를 검사합니다.

비용 분해 대조군의 사전 생성 값 `Database.Update`는 1,000회에 680~810ms,
선택 게시 전체 경로는 780~970ms였습니다. 잠금·누적은 20ms,
모델 읽기는 10ms, 값 생성은 110~170ms였습니다. 각각 별도 루프의 관측값이므로
합산/차감에 의한 정확한 호출 비용 분석은 아닙니다. 특히 0~20ms 관측값은 타이머 해상도의
영향을 크게 받습니다. 큰 모델의 전체 순회를 피하는 것이 가장 큰 개선이며,
선택 API만 추가했다고 전체 `Publish()`가 빨라지는 것은 아닙니다.

동일 보드에서 얻은 최종 비교입니다. 전체 게시 시간은 **100회 합계**,
첫/마지막 인덱스 선택 게시 시간은 각각 **1,000회 합계**이며 모두 변경 없는 경로입니다.
최적화 전 전체 시간은 최초 실물 결과를 사용합니다.

| Point / 용량 | 전체 게시 전 | 전체 게시 후 | 선택 첫 인덱스 | 선택 마지막 인덱스 | 계측 포함 앱 PE | 앱 PE 증가 |
|---|---:|---:|---:|---:|---:|---:|
| 8 / 16 | 590 ms | 570 ms | 710 ms | 720 ms | 6,988 B | 1,048 B |
| 8 / 128 | 590 ms | 550 ms | 720 ms | 700 ms | 6,996 B | 1,048 B |
| 32 / 16 | 2,630 ms | 2,410 ms | 760 ms | 770 ms | 10,900 B | 1,868 B |
| 32 / 128 | 2,670 ms | 2,390 ms | 790 ms | 750 ms | 10,904 B | 1,864 B |
| 128 / 16 | 11,670 ms | 10,470 ms | 830 ms | 800 ms | 26,580 B | 5,128 B |
| 128 / 128 | 11,670 ms | 10,510 ms | 820 ms | 850 ms | 26,592 B | 5,132 B |

128개 모델의 전체 게시 한 번은 약 116.7ms→104.7~105.1ms로 약 10% 감소했습니다.
한 Point만 게시하면 0.80~0.85ms이므로 변경 대상을 아는 앱에서 효과가 가장 큽니다.
모든 Point를 하나씩 선택 호출하는 방식은 전체 게시와 잠금·스냅샷 계약이 다르므로 권장하지 않습니다.
이는 통신 RTT나 값이 변경되어 이벤트를 생성하는 경로의 시간 보장이 아닙니다.

모델 및 바인딩·잠금 객체·Database의 RAM은 여섯 조합 모두 최초 표와 동일합니다.
추가 캐시/Point 배열은 없습니다. 계측 포함 앱 PE 증가에는 선택 분기와 새 벤치마크가
함께 포함되므로 선택 API만의 순수 크기 증가로 해석하지 않습니다.
진단 배열 확장만으로도 별도로 64 B의 페이로드 저장 공간이 추가되며,
이는 모델·바인딩 생성 전에 이미 할당되어 위 RAM 차이 측정에 포함되지 않습니다.
core PE는 10,604→10,596 B, Outstation PE는 8,160→8,172 B로 런타임 합계는 4 B 증가했습니다.

대조군과 최종 실행 모두 샘플 128회, 여섯 조합 각각 준비 3회+측정 100회 순회를 통과했습니다.
최종 실행의 직접 계측 전후 및 준비 후 GC 11개 표본 잔류 증가도 모두 0 B입니다.
작은 이벤트 용량 두 조합의 의도한 103회 Overflow와 모든 Static 갱신,
Confirmation 후 이벤트 제거·Overflow 해제를 그대로 확인했습니다.
두 실행 모두 첫 복원 시도에서 원래 Modbus 앱 복원과 COM6 읽기를 통과했습니다.

## 최신 견고성 재검증 (2026-10-29)

`bin\dnp3-mapping-hardware-20261029-112507`에서 독립 원본 OpenDNP3 Master로
샘플 256회와 **8/32/128 Point × 이벤트 용량 16/128**의 여섯 조합을 재검증했습니다.
각 조합의 100회 전체 순회와 별도 선택 게시·Flags/Timestamp·Deadband 경계 검사,
이벤트 수신·Confirmation 후 제거를 모두 통과했습니다.
100회 순회의 준비 후 GC 보존 힙 증가는 각 0 B였습니다.
32/128 Point·용량 16의 각 103회 Overflow는 의도한 검사이며, 나머지 조합은 0회였습니다.
원래 Modbus 앱 복원과 COM6 읽기도 통과했습니다.

Master TCP의 피어 재시작·강제 단절, 양 역할 TCP/Serial의 CRC·부분 프레임 만료 및
Serial ACK/응답 Timeout 검사는 별도 시험입니다.
최신 `dnp3-master-soak-20261029-115537`·`-120122`·`-120508`·`-121035`의 범위는
[Master 샘플](../../../Samples/DNP3/VagabondK.nF.DNP3.MasterMapping/README.md)과
[전체 검증 대조표](../../../Samples/MappingCoverage.md)를 참조하십시오.
Outstation 여섯 조합의 게시/GC 수치를 Master·Serial 통신 비용으로 해석하지 않습니다.

## 시험 준비 과정의 실패와 수정

첫 샘플 시험(`bin\dnp3-mapping-hardware-first`)은 원본 피어의 첫 요청에서
`FAILURE_NO_COMMS`로 종료되었습니다. 별도로 통신 바이트를 직접 조회했을 때는 MCU의 정상 응답을 확인했습니다.
피어의 `READY`는 프로세스·프로토콜 스택 초기화일 뿐 TCP 채널 연결 완료가 아니므로,
시험 드라이버에 채널 상태 출력을 추가하고 **`CONNECTED`를 확인한 뒤 요청**하도록 수정했습니다.
OpenDNP3/ser4cpp 라이브러리는 수정하지 않았으며 요청 제한 시간을 늘리거나
실패한 본 시험을 자동 재전송하여 통과시키지 않았습니다.
진단용 별도 배포에서는 일시적 nanoff E2001도 한 번 있었고, 재시도 뒤 복원했습니다.

다음 실행(`bin\dnp3-mapping-hardware-ready`)은 샘플 128회와 8/32개 네 조합을
통과했으나 128개 앱의 TCP 준비 제한 시간 90초를 초과했습니다.
TCP를 열기 전에 수행하던 1,000회 전체 Publish 계측이 큰 모델에서 기동 예산을 초과하는 구조였습니다.
최종 계측은 모든 규모에서 **100회**로 통일했습니다.
작은 모델도 약 0.6초의 측정 구간이므로 약 10ms 타이머보다 충분히 길며, 준비 제한 시간은 유지합니다.
실패한 실행도 finally 복원과 COM6의 원래 Modbus 읽기를 통과했습니다.
