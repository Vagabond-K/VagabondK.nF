# SNMP 매핑 MCU 자원·견고성 검증

`Build\Test-SnmpMappingScaling.ps1`가 이 폴더의 계측 `Program.cs`와
8/32/128개 스칼라 모델을 `bin` 아래에 조합해 실제 nanoFramework 실행 이미지를 만듭니다.
각 모델은 **쓰기 가능한 Integer32 N-1개와 512바이트 OctetString 1개**로 구성됩니다.
문서용 enterprise 32473의 `.30`은 모델, `.31`은 14개 계측 OID입니다.
운영 앱이나 일반 보드에 배포하지 마십시오.

```powershell
.\Build\Test-SnmpMappingScaling.ps1 -AllowDeviceChanges -Rounds 100 `
  -OutputPath .\bin\snmp-scaling-new-run
```

이 명령은 전용 Geekble Nano ESP32-S3(COM3, 저장 Wi-Fi, 기본 IP 192.168.0.187)를 사용합니다.
평가용 community public/private는 평문입니다. 방화벽·Wi-Fi·펌웨어는 변경하지 않습니다.
모든 이미지를 먼저 빌드하고 원래 이미지 SHA-256을 검사한 후 배포합니다.
COM3 디버거/시리얼 모니터를 닫아 두십시오. 실행 중 `Debugger.IsAttached`가 true이면 실패합니다.
세 규모를 순차 배포하며 일시적 nanoff 연결 실패는 로그와 경고를 남기고 최대 3회 시도합니다.
장치 변경을 시작하면 `finally`에서 원래 Modbus 앱을 복원하고 COM6 RTU 읽기로 확인합니다.
복원 실패는 한 번만 명시적으로 재시도하며 재실패하면 오류로 끝납니다.

## 측정 정의

| 항목 | 범위 |
|---|---|
| MappingPEBytes | 생성 모델과 **계측 코드 전체**의 PE. 순수 매핑 코드만의 크기는 아님 |
| CorePEBytes | SNMP 런타임 PE |
| DeploymentBytes | 시스템 의존성을 포함한 실행 이미지. 펌웨어 크기는 제외 |
| ModelStoreBytes | 강제 GC 후 모델·공유 잠금 객체·생성 저장소의 생성 전후 가용 힙 차이 |
| AgentAndMetricsBytes | Agent 및 계측 래퍼·정의 14개의 생성 전후 차이. 순수 Agent 비용과 구분 불가 |
| DirectNumericMs | 미리 만든 SnmpValue 1개로 N-1개 숫자에 SET→Read를 100회 순회하는 MCU 시간 |
| OctetValidationMs | 미리 만든 512바이트 SnmpValue의 AcceptsWrite 3,000회 MCU 시간 |
| NetworkMs | 요청 송신부터 응답 수신까지 PC 측 UDP RTT. BER 파싱 검증 시간은 제외 |
| GcSamples | 모든 패킷 도우미의 지역 변수 수명이 끝난 후 강제 GC로 얻은 가용 힙 |

직접 호출 시간은 `Environment.TickCount64` 해상도(실물 약 10ms)의 제한을 받습니다.
숫자 읽기의 SnmpValue 생성 비용은 포함되지만 새 SET 값 생성 비용은 제외됩니다.
Octet 길이 검증 시간은 **SET 전체나 모델 배열 복사 시간은 아닙니다**.
최적화 전후 숫자 루프는 대조군이고 Octet 루프가 길이 검사 비용 비교군입니다.

라이브러리 인코더와 별도로 작성한 **자체 BER 시험기**
`Tests\SNMP\VagabondK.nF.SNMP.Mapping.Tests\Scaling.cs`가 8개씩 배치하여
SET→GET→GETBULK를 각 규모에서 기본 100회 순회합니다.
이 규모 시험은 SharpSnmpLib 외부 라이브러리 상호운용 시험이 아닙니다.
매번 OID 순서·바인딩 개수·숫자와 512바이트 데이터의 일치를 검사합니다.
한 패킷의 반환 값 수는 최대 8개이며 **128개를 한 응답에 담는 시험은 아닙니다**.
초기 연결 중 시간 초과·연결 초기화만 제한적으로 재시도하고 본 시험 패킷은 재시도하지 않습니다.
세 번 전체 순회와 계측 명령 자체를 준비 단계에 포함한 뒤 기준 GC 표본을 얻습니다.
이후 10회 순회마다 GC 표본을 채취하고 기준 대비 최대 잔류 증가가 **0 B**인지 검사합니다.
규모당 기준 포함 11개 표본이며, 준비 전후 힙 변화는 잔류 증가와 구분합니다.

`sizes.csv`에는 이미지 SHA-256과 크기, 각 규모 `measurements.json`에는 raw GC 표본과
RTT 최솟값·중앙값·P95·최댓값, 숫자·Octet 처리 시간 및 요청 수를 기록합니다.
배포/피어/복원 로그와 생성 모델도 같은 폴더에 남깁니다.
측정 대상은 힙의 **GC 후 잔류량**이며 힙 최대 사용량·할당 총량·스택·네이티브·Wi-Fi 메모리를 나타내지 않습니다.
전원 재투입 후 동작이나 수시간·수일의 안정성도 보장하지 않습니다.
배포별 시작 가용 힙은 펌웨어의 네트워크 상태에 따라 달라지므로 절대값 대신
해당 부팅 내 생성 전후 차이와 준비 후 표본을 비교합니다.

PC의 `AllocationCost` 회귀는 허용되는 32바이트 값과 거절되는 512바이트 값을 미리 만든 뒤 각각
10,000회 길이를 검사하고 해당 스레드의 추가 할당이 0 B인지 확인합니다.
이는 MCU 할당량을 대신하는 수치가 아니라, 복사 제거를 정밀 검증하는 별도 시험입니다.

## 실물 전후 결과 (2026-10-25)

최적화 전 증거는 `bin\snmp-scaling-before-complete`, 후 증거는
`bin\snmp-scaling-after`입니다. 동일한 계측 소스·모델 프로파일·Release 빌드와
디버거 없는 보드에서 규모당 100회 전체 순회를 수행했습니다.
처음 부분 실행 `bin\snmp-scaling-before`는 8개 측정 후 다음 배포에서 nanoff E2001로
중단됐으며 원래 앱은 복원했습니다. 이를 전체 성공 결과에 합산하지 않았습니다.
최종 전/후 실행은 모두 원래 Modbus 앱 복원과 COM6 읽기까지 첫 복원 시도에 통과했습니다.

| 매핑 수 | 모델+잠금 객체+저장소 RAM (전=후) | Agent+계측 RAM (전=후) | 계측 포함 앱 PE 전→후 | 배포 이미지 전→후 |
|---|---|---|---|---|
| 8 | 1,788 B | 4,092 B | 5,880→5,904 B | 95,316→95,384 B |
| 32 | 5,244 B | 4,716 B | 11,428→11,452 B | 100,864→100,932 B |
| 128 | 19,068 B | 7,212 B | 33,672→33,692 B | 123,108→123,172 B |

SNMP core PE는 12,820→12,864 B로 44 B 늘었습니다.
생성 모델/정의 배열 RAM은 줄지 않았습니다. 개선 대상은 영구 메모리가 아닌
OctetString **길이만 검사할 때 생성되던 임시 배열**입니다.
`ByteLength`는 길이만 반환하고 내부 배열을 노출하지 않습니다.
`GetBytes()`와 SET 적용 시 모델이 소유할 배열 복사는 그대로 유지했습니다.

| 매핑 수 | 숫자 SET→Read 100회 순회 전→후 | 512 B Octet 길이 검사 3,000회 전→후 | 준비 후 최대 잔류 증가 전/후 |
|---|---|---|---|
| 8 | 170→170 ms (700쌍) | 630→180 ms | 0 / 0 B |
| 32 | 710→710 ms (3,100쌍) | 620→180 ms | 0 / 0 B |
| 128 | 3,000→2,980 ms (12,700쌍) | 620→190 ms | 0 / 0 B |

길이 검사 MCU 시간은 이 반복 측정에서 약 69~71% 감소했습니다.
PC의 32바이트 허용·512바이트 거절 검사 각 10,000회의 임시 할당은
5,920,000→0 B였으며, 이를 MCU 할당 바이트로 해석하지 않습니다.
준비 후 GC 가용 힙은 전후 모든 규모에서 각각 11개 표본이 동일했습니다.
직접 호출 숫자 대조군은 사실상 같으며 이 측정만으로 숫자 매핑의 속도 향상을 주장하지 않습니다.

| 매핑 수 | GET RTT 중앙값 전→후 | GETBULK RTT 중앙값 전→후 | SET RTT 중앙값 전→후 |
|---|---|---|---|
| 8 | 28.67→28.52 ms | 24.69→24.74 ms | 20.10→19.73 ms |
| 32 | 29.16→28.95 ms | 25.20→25.24 ms | 19.86→19.77 ms |
| 128 | 30.03→30.01 ms | 26.17→26.18 ms | 20.58→20.55 ms |

RTT는 최대 8개 바인딩 배치의 왕복이며, 일부 배치만 512 B OctetString을 포함합니다.
실제 LAN RTT 차이는 작고 측정 변동 범위 안에 있으므로 전체 SNMP 통신 성능이 개선됐다고 주장하지 않습니다.
전/후 각각 성공 응답 6,606개(측정 요청 6,300개와 준비·계측 요청)를 검증했습니다.
초기 UDP 준비 시간 초과 외 본 시험 오류·재전송은 없었습니다.
128개 기준 모델·저장소와 Agent·계측 합계는 26,280 B이지만,
이는 응답 버퍼·임시 배열·스택·네이티브 메모리를 포함한 전체 RAM 예산이 아닙니다.
따라서 이번 범위에서는 추가 복잡한 캐시·공유 가변 값·Agent 정렬 재설계를 도입하지 않았습니다.

## 외부 피어 견고성·배열 소유권·동시 스냅샷

규모 측정과 별도로 `Robustness.nfproj`는 실제 샘플 모델의 UDP 1161 Agent와
시험용 UDP 1162 진단 채널을 구동합니다. 다음 명령은 보드를 변경하므로 같은 전용 장치·복원 절차가 필요합니다.

```powershell
.\Build\Test-SnmpMappingHardware.ps1 -AllowDeviceChanges -Robustness -Iterations 256
```

정상 SMI 형식 왕복·다중 SET 사전검증과 로컬 첫/중간/마지막 변경의 격리는
외부 **SharpSnmpLib 12.5.7**이 요청/응답을 인코딩·디코딩합니다.
두 번째 OID arc ≥40 경계는 외부 구현의 제한 때문에 보조 `Wire.cs` BER 시험으로 구분합니다.
64회 혼합 고장 순회마다 마지막 varbind의 wrongType으로 앞선 유효 항목까지 모두 적용되지 않는지,
비정상 데이터그램 송신 뒤 정상 GET과 모델 값 보존을 확인합니다.
이는 사전검증 실패의 값 보존이지 setter 예외 시 롤백/전체 SET 원자성의 보장이 아닙니다.
4096바이트 UDP 송신도 포함하지만 장치 측 도달/거절 계수는 없으므로
대용량 데이터그램의 애플리케이션 크기 제한 검증으로 간주하지 않습니다.

네트워크 기동 전에 `Robustness.cs`가 byte[]/OID 읽기 반환값과 SET 입력의 소유권 분리를 검사합니다.
byte[] 동시 변경/읽기와 `SnapshotChecks.cs`의 Modbus 다중 워드 스칼라,
BACnet 값/품질, DNP3 값/Flags/시각은 앱과 매핑이 **동일한 잠금**을 사용할 때를 검사합니다.
각 writer는 800회 갱신하고 reader는 최소 800회 관찰합니다.
개별 값/Point의 스냅샷 시험이며 요청 전체나 여러 Point의 원자적 갱신을 보장하지 않습니다.
여러 프로토콜 참조는 이 보조 시험 이미지에만 필요하며 SNMP 제품의 런타임 의존성이 아닙니다.

2026-10-29 `bin\snmp-mapping-hardware-20261029-122940`에서 외부 피어 256회와
위 64회 견고성 순회를 완료했습니다. 혼합 구간의 GC 후 보존 힙 증가는 **144 B**
(허용 256 B)이며 무할당이나 누수 부재를 의미하지 않습니다.
별도 `bin\snmp-scaling-20261029-123740`은 자체 BER 시험기로
8/32/128 OID·512바이트 OctetString의 GET/GETBULK/SET 각 100라운드를 완료했고,
준비 후 GC 보존 힙 증가는 각 0 B였습니다. 두 실행 모두 원래 앱 복원·COM6 읽기를 통과했습니다.
