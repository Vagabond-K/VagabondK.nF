# Modbus 정적 매핑 실물 검증

전용 Geekble Nano ESP32-S3(nanoFramework, 배포 COM3, Wi-Fi `192.168.0.187`)와
PC `192.168.0.210` 사이에서 TCP 15020으로 실행하는 **평가용 시험**입니다.
독립 피어는 Python의 **pymodbus 3.11.3**이며 VagabondK 프로토콜 코드를 참조하지 않습니다.
센서·GPIO·실제 설비를 제어하지 않고 전용 모델과 테스트 값만 사용합니다.

## 구성과 실행

- `Program.cs`·`Models.cs`: 실제 MCU Slave/Server 및 Master/Client 시험 앱.
- `Generate-ScaleModel.ps1`: 8·32·128개의 ushort Point를 가진 시험 모델을 `obj`에 생성합니다.
  MSBuild의 `MappingScaleCount`로 선택하며 수동 변경 파일이 아닙니다.
- `peer.py`: 독립 PC Master/Slave. 정상 요청 외에 예외 응답·응답 지연·연결 종료·Transaction/Unit ID 불일치를 주입합니다.
- `Build\Test-ModbusMappingHardware.ps1`: 피어 자체 검증, 모든 이미지 빌드, 배포·통신 검사, 결과 보관, 원래 앱 복원.

```powershell
py -3.14 -m venv .\Tests\Modbus\VagabondK.nF.Modbus.Mapping.Hardware\bin\python
.\Tests\Modbus\VagabondK.nF.Modbus.Mapping.Hardware\bin\python\Scripts\python.exe -m pip install -r .\Tests\Modbus\VagabondK.nF.Modbus.Mapping.Hardware\requirements.txt
.\Build\Test-ModbusMappingHardware.ps1 -AllowDeviceChanges
```

Visual Studio nanoFramework/MSBuild, .NET SDK, PowerShell 7과 `nanoff`가 필요합니다.
SSID·Password는 Device Explorer에 저장된 AutoConnect 설정을 사용하며 스크립트가 변경하지 않습니다.
PC의 네트워크 주소와 TCP 15020 방화벽 허용은 사용자가 미리 준비해야 합니다.
스크립트는 방화벽·네트워크 설정을 자동 변경하지 않습니다.
장치·주소를 바꾸려면 시험기의 `PeerAddress`와 스크립트·복원 절차를 함께 검토하십시오.
COM3는 반드시 다른 작업이 사용하지 않는 전용 평가 보드여야 합니다.

Master/Slave 앱은 `MappingHardwareRole=Master|Slave`로 선택합니다.
이미지는 빌드할 뿐 솔루션 빌드만으로 배포하지 않습니다.
모든 Slave 변형은 동일한 Scalar 모델을 검증하고, Scale 모델의 Point 수만 달라집니다.
PC Master의 반복 수는 스크립트 `-Iterations`(기본 64)이며 MCU 내부 매핑 측정 반복 수와는 별개입니다.

## 디버거 없는 안정성 시험

```powershell
.\Build\Test-ModbusMappingHardware.ps1 -AllowDeviceChanges -NoDebugger -StabilitySeconds 120 -SlaveRuns 2
```

`-NoDebugger`에서는 배포 도구가 종료한 뒤 Debug Engine을 연결하지 않고,
MCU가 Input Register 1031에 보고하는 `Debugger.IsAttached`가 false인지 확인합니다.
8·32·128 Point 각각 2번 배포·CLR 재시작하며 각 실행에서 준비 단계 후 최소 120초 동안 반복합니다.
**전원을 물리적으로 차단하는 시험은 아닙니다.** 수동 전원 시험이나 별도 전원 제어 장비를 대체하지 않습니다.
특정 크기만 시험하려면 `-ScaleCounts 8` 등을 지정합니다.
`StabilitySeconds`는 0(비활성) 또는 60~3600이며, 반복 배포는 `NoDebugger`에서만 지원합니다.

정상 값 읽기 → 부분 쓰기 거절 → 값 불변 확인을 연결당 10회 수행한 뒤 연결을 바꿉니다.
재연결 준비 단계에서는 잘못된 MBAP Protocol ID와 불완전 헤더를 보내,
연결 종료 및 Server의 10초 수신 Timeout 이후에도 새 연결에서 정상 통신하는지 검사합니다.
응답 Timeout은 기본 **2초, 재송신 0회**입니다.
`-ResponseTimeoutSeconds`는 지연 원인 진단용이며 이 값을 늘린 실행을 기본 기한 통과로 해석하지 마십시오.

정상 EOF·잘못된 MBAP·전송 Timeout 등 기존 Transport의 예외 경로는 여전히 존재합니다.
디버거 없는 nanoCLR의 예외 진단 지연을 고려해 연결 사이에 4초를 둡니다.
따라서 이 시험은 **즉시 재연결이나 무중단 다중 Client 수용을 보장하지 않습니다.**
이는 같은 연결에서 잘못된 주소 요청에 Exception 응답을 보내는 경로와 구분합니다.

진단 Register 1022~1027은 연결 수·완료 응답 수·Exception 응답 수·Timeout·연결 종료·Socket 오류 수를 보고합니다.
카운터는 ushort 범위에서 순환하며 시험용입니다. Register 1101에 `0xCAFE`를 쓰면 강제 GC 후 가용 힙을 1029~1030에 기록합니다.
초기 연결, MBAP 오류, 수신 시간 초과, 두 번의 재연결까지 실행한 후 안정성 시험의 힙 기준을 잡습니다.
초기 경로 준비에 따른 감소도 `startup_growth_bytes`로 별도 보존하며, 측정 구간의 어느 GC 표본이든
기준 대비 감소가 256바이트를 넘으면 실패합니다. 준비 단계 이전의 메모리 감소를 0으로 간주하지 않습니다.

각 요청·응답의 PC 시간·원시 패킷은 `*.wire.jsonl`, 각 연결의 힙·카운터는 `*.stability.json`에 저장합니다.
MCU 모델 값·거절 응답·오류 복구·잔류 힙 검사까지 모두 통과해야 `SLAVE PASS`를 출력합니다.
실패 때도 원시 표본과 복원 결과를 보존하며 자동 재시도로 실패 요청을 통과시키지 않습니다.

### 비계측 최종 결과 (2026-10-25)

`bin\mapping-hardware-20261025-163350`에서 위 6개 실행을 모두 통과했습니다.
디버거 없이 준비 단계 이후 측정한 시간의 합계는 **738.05초(약 12.3분)**이며,
이는 12분 연속 단일 실행이 아니라 크기별 2회 실행의 합계입니다.
진단 표본에서 총 190개 연결과 1,828개의 정상적인 Modbus Exception 응답을 확인했습니다.
연결 수에는 의도적으로 잘못된 헤더를 보낸 연결도 포함됩니다.

| 매핑 수 | 배포·재시작 횟수 | 정상 통신 검사 연결 수 합계 | 오류 경로 준비 중 가용 힙 감소 | 준비 후 최대 잔류 힙 증가 | 읽기→거절→읽기 최장 |
|---|---:|---:|---:|---:|---:|
| 8 | 2 | 59 | 각 288바이트 | 0바이트 | 316.58 ms |
| 32 | 2 | 59 | 각 288바이트 | 0바이트 | 350.17 ms |
| 128 | 2 | 60 | 각 288바이트 | 0바이트 | 74.43 ms |

최장 시간은 세 요청의 합계이며 개별 요청의 2초 기한과 구분합니다.
모든 실행에서 불완전 헤더 Timeout 1회와 잘못된 MBAP 연결 종료 후 정상 통신을 확인했습니다.
Master 정상 읽기 816건·쓰기 9건·오류 3단계도 다시 통과하고 원래 앱의 COM6 복원을 확인했습니다.
최종 실행 메타데이터와 실시간 디버거 플래그 검사 보완 후
`bin\mapping-hardware-20261025-165545`에서도 8 Point 기본 비계측 시험과 Master 시험·복원을 재확인했습니다.

이는 **제한된 시간의 반복 검증**이지, 수 시간·수일 연속 운전이나 전원 차단 복구의 보증은 아닙니다.
준비 중 감소한 288바이트를 누수 없음으로 덮어쓰지 않으며,
그 이후의 강제 GC 표본이 이번 실행 동안 일정했음을 확인한 것입니다.
실제 힙 최대 사용량·스택·호출 중 임시 할당량 및 TCP가 아닌 전송 방식은 이 시험으로 측정하지 않았습니다.

## 검증 범위

MCU Slave에서는 다음을 독립 PC Master가 확인합니다.

- 부호 있는/없는 16·32·64비트 정수, float32/float64의 선택된 경계값 37종을 정확한 비트로 비교합니다.
  정수 극값, 음의 0, 양/음의 최소 subnormal, 최대 유한값, 양/음의 Infinity와 대표 quiet NaN을 포함합니다.
  모든 NaN payload나 모든 IEEE754 비트 조합의 보존을 보장하는 시험은 아닙니다.
- 상위·하위 워드 및 바이트 순서. 전송 값의 왕복뿐 아니라 MCU의 실제 형식별 값도 검증용 명령으로 비교합니다.
- 9개 모델 멤버를 하나씩 로컬 변경한 뒤 외부 읽기로 해당 멤버만 바뀌었는지 확인하고,
  외부 쓰기로 복원합니다. 경계값 쓰기에서도 이웃 주소가 그대로인지 전체 구간을 비교합니다.
- Coil 쓰기/읽기, Discrete Input, signed Input Register, private Setter 접근.
- 전체·부분 Register 읽기, 빈 주소, 끝 주소 초과, 읽기 전용 주소 쓰기, 다중 Register 부분 쓰기 거절.
- 잘못된 요청에 IllegalDataAddress를 반환하고 앞서 포함된 올바른 멤버도 변경하지 않는지 검사.
- 8·32·128 Point를 실제 통신으로 모두 읽고 쓰며, 123/125 Register 요청 경계 분할을 확인.

MCU Master에서는 독립 PC Slave가 정상·선택 그룹 읽기 요청 **818개**, 생성된 쓰기 **9개**를 검사합니다.
전체 읽기 816개에 `Status` Coil 읽기 1개와 `Settings` Register 읽기 1개를 추가하여,
그룹이 다른 멤버를 갱신하지 않는지 MCU의 형식별 값과 정확한 전송 요청 목록으로 확인합니다.
Register 요청 상한 4개·비트 상한 2개, 값 하나를 나누지 않는 병합 결과와 순서를 확인합니다.
MCU는 실제로 수신한 형식별 값을 검사한 뒤 쓰기 메서드를 명시적으로 호출합니다.
예외 응답 → 시간 초과 → 연결 종료 → 잘못된 Transaction ID → 잘못된 Unit ID의
5단계를 차례로 검출하고, 오류 응답으로 모델이 바뀌지 않는지 검사합니다.
각 단계 뒤 연결을 새로 만들어 최종 정상 수신과 완료 표식까지 확인합니다.
피어의 `selftest` 모드는 localhost에서 같은 시나리오를 pymodbus Client로 먼저 검사합니다.
고정 버전 pymodbus의 연결 Handler를 사용하는 연결 종료 주입은 테스트에만 존재합니다.

Timeout·연결 종료는 의도된 오류이므로 피어 로그에 `No response received` 또는 `Cancel send, because not connected`가
나올 수 있습니다. 완료 표식, 정확한 요청 목록, 오류 단계 및 종료 코드가 모두 일치해야 성공입니다.
발생한 오류를 무조건 무시하거나 재시도하여 성공 처리하지 않습니다.

Wi-Fi 연결과 2초 대기를 마친 뒤 배열·Lock을 미리 만들고, 모델과 생성 저장소 전후에
`nanoFramework.Runtime.Native.GC.Run(true)`의 가용 힙을 읽습니다.
100회 예열 후 1,000회씩 3개 배치를 실행하며 매 배치 후 강제 GC로 가용 힙을 기록합니다.
측정 구간은 같은 모델의 `WriteHoldingRegisters` + `ReadRegisters` 직접 호출이며,
네트워크 왕복 시간·Socket/Server 할당·프로토콜 파싱은 시간에 포함하지 않습니다.
측정 후 별도 TCP 통신으로 결과를 읽고 Scalar/전체 Scale 모델을 검증합니다.

힙 감소에는 모델 필드·생성 저장소 객체·작업용 배열이 포함되며,
앞서 생성한 호출자 배열·잠금 객체와 나중에 생성한 ModbusServer/Socket은 제외됩니다.
바이트코드 크기는 Scalar·원격 모델·측정·시험 로직까지 포함한 **시험기 앱 PE**이지 매핑 코드만의 크기가 아닙니다.
Debug Engine이 연결된 상태에서 측정했으며 네트워크/런타임 작업도 동작합니다.
따라서 다른 펌웨어·보드의 처리 시간이나 메모리와 같다고 보장하지 않습니다.

예열 대비 및 마지막 두 배치 사이의 회수되지 않은 힙 증가가 256바이트를 넘으면 검사는 실패합니다.
위 실행에서는 세 배치 모두 증가가 0이었습니다. 이는 **임시 할당 없음·GC 정지 없음·스택 사용량 0**의 증명이 아닙니다.
스택 및 호출 중 최대 힙 사용량은 측정하지 않았습니다.
이 2026-10-25 실행은 NaN/Subnormal 경계값의 실물 시험 전 기록입니다.
아래 최신 재검증은 대표 비트 패턴을 추가하지만 모든 IEEE754 값의 완전 탐색은 아닙니다.
이번 전송은 Wi-Fi TCP이며 RS-485/RTU/ASCII 매핑의 별도 실물 시험은 아닙니다.

부분 쓰기 거절 응답이 약 **3.51초** 후 도착했습니다. 영구 정지가 아니라 기본 2초 기한 초과였습니다.
다른 주소 거절도 약 2.01~3.51초가 걸렸습니다. 런타임 내부 지연의 모든 원인까지 분리 측정한 것은 아닙니다.

예상 범위 오류에 관리 예외를 던지던 경로 대신 선택형 `IModbusDataStoreValidator`를 도입하고,
생성 저장소와 Server가 고정 주소를 사전 검증해 Exception 응답을 직접 생성하도록 변경했습니다.
손으로 작성한 기존 저장소의 예외 처리와 직접 저장소 호출의 주소 예외는 유지합니다.
Getter/Setter의 예기치 않은 예외를 성공으로 바꾸거나 숨기지 않습니다.
후속 `mapping-hardware-20261025-162637`에서는 기본 2초 기한으로 8 Point 비계측 시험을 통과했고,
읽기·거절·읽기 한 묶음의 최장 시간은 약 58ms였습니다.

`mapping-hardware-20261025-162959`의 첫 안정성 실행은 최초 오류 경로 실행 전 대비 288바이트 감소로 실패했습니다.
모든 원시 표본을 남겼으며 이후 20개 표본은 같은 가용 힙이었습니다.
이에 오류 경로와 두 번의 재연결을 준비 단계에 포함하고, 초기 감소와 준비 후 증가를 따로 보고하도록 했습니다.
256바이트 허용값은 늘리지 않았습니다. 이 관찰만으로 초기 감소의 내부 원인이나 장기 누수 부재를 단정하지 않습니다.

읽기 그룹 추가 후 `bin\mapping-hardware-20261025-170903`에서 디버거 없이 MCU Master의
그룹별 독립 갱신·818개 읽기·9개 쓰기·오류 3단계, MCU Slave 8 Point 및 COM6 원래 앱 복원을 통과했습니다.
앞서 기록한 816개 수치는 그룹 기능 추가 전 실행의 실제 결과입니다.

다음 `mapping-hardware-20261025-160208`에서는 32 Point 측정의 힙 증가 검사가 실패했습니다.
당시 측정은 Wi-Fi 초기화와 겹칠 수 있었고 원시 측정값이 저장되기 전에 실패했습니다.
측정 창을 네트워크 연결 이후로 옮기고 3배치 원시 결과를 먼저 저장하도록 보완한 최종 실행은 통과했습니다.
이 실패만으로 매핑 자체의 누수를 확인하거나 반증했다고 단정하지 않습니다.
통과를 위해 힙 허용값을 늘리지는 않았습니다.

## 복원과 안전

Modbus TCP는 인증·암호화가 없으므로 신뢰할 수 있는 격리 LAN에서만 실행하십시오.
스크립트는 배포 전에 `bin\hardware\restore-Modbus.SerialServer.bin`의 SHA256을 확인합니다.
배포 시도 이후에는 성공·실패와 무관하게 `finally`에서 `Restore-ModbusHardware.ps1`을 호출합니다.
이 절차는 지정된 원래 앱으로 복원하는 것이며 임의로 연결한 보드의 현재 앱을 백업해 주는 기능이 아닙니다.
복원 후 COM6의 RS-485 RTU 읽기로 HoldingRegister 0~2가 `123,456,65535`인지 확인합니다.
최종 성공 및 앞선 실패 실행에서도 이 복원이 통과했습니다.
