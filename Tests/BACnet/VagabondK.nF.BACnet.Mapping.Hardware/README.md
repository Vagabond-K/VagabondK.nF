# BACnet 매핑 실물·MCU 자원 측정

전용 Geekble Nano ESP32-S3의 실제 UDP47808 Device를 외부 **BACnet 4.0.0** 클라이언트로 시험합니다.
소스 Generator/샘플부터 기능 시험, 규모별 메모리/시간·GC 확인, 원래 앱 복원까지 수행합니다.
기존 Device의 최대 객체 수 64개 계약을 유지하므로 **8·32·64개**를 측정합니다.
이 시험을 위해 런타임 한도를 128개로 늘리지 않습니다.

```powershell
.\Build\Test-BacnetMappingHardware.ps1 -AllowDeviceChanges -Iterations 128 -Rounds 100 `
  -OutputPath .\bin\bacnet-mapping-new-run
```

일반 사용자 보드에 그대로 실행하지 마십시오. 전용 구성은 COM3 배포,
저장 Wi-Fi/IP 192.168.0.187, 원래 Modbus 앱의 RS-485 COM6입니다.
시리얼 모니터/디버거를 닫고 실행합니다. 펌웨어·Wi-Fi·자격증명·방화벽은 변경하지 않습니다.
BACnet과 진단 UDP에는 인증/암호화가 없으므로 격리 LAN에서만 사용합니다.

## 안전 절차와 통신 범위

원래 이미지 `bin\hardware\restore-Modbus.SerialServer.bin`의 SHA-256
`66C51145509667EA4019649750B42CAD47344CE76D9736994B9658E0F45226A7`과 COM3를 먼저 확인합니다.
PC 시험과 모든 MCU 이미지를 빌드한 후 장치를 변경합니다.
샘플은 Who-Is/I-Am, Device가 먼저 나오는 Object_List와 인덱스별 읽기, AV/BV 쓰기·읽기,
음의 0/subnormal/유한 float32 경계값, 품질→Fault/Reliability, readonly·wrong type·
비유한값·priority 거절, 잘못된 패킷 뒤 복구를 시험합니다.
외부 클라이언트는 기본적으로 본 시험의 재전송 횟수를 0으로 두며 실패를 숨기지 않습니다.
발견 단계만 준비 기한 내 Who-Is를 반복합니다.

nanoff 배포 연결 오류는 로그와 경고 후 최대 3회 시도합니다.
장치 변경을 시작한 뒤에는 `finally`에서 원래 Modbus 앱을 복원하고 COM6 RTU
9600 8E1 holding0..2=123/456/65535를 읽어 확인합니다.
복원 실패는 한 번만 명시적으로 재시도하고 재실패하면 오류로 종료합니다.
중간에 시험이 실패해도 원래 앱을 복원하며, 실패 로그를 성공 결과로 간주하지 않습니다.

## 측정 계약

규모별 모델은 절반이 쓰기 가능한 float AV, 절반이 쓰기 가능한 bool BV이고,
각 종류의 인스턴스 번호는 0부터 시작합니다. 공유 잠금 객체를 포함한 모델·저장소를 한 번 생성합니다.
시험용 Program과 모델을 `bin` 아래에 생성하며 `Program.cs` 원본은 이 폴더에 있습니다.

| 항목 | 정의 |
|---|---|
| MappingPEBytes | 모델·생성 저장소·float helper·계측 코드 전체의 PE. 순수 매핑 코드 크기는 아님 |
| CorePEBytes | BACnet 런타임 PE |
| DeploymentBytes | 시스템 의존성 포함 배포 이미지. 펌웨어 크기는 제외 |
| ModelStoreBytes | 강제 GC 후 모델·공유 잠금 객체·생성 저장소의 생성 전후 가용 힙 차이 |
| DeviceBytes | 기존 BacnetDevice 생성 전후 가용 힙 차이 |
| DirectAnalogMs / DirectBinaryMs | 각 종류 모든 객체의 쓰기→읽기를 100회 순회한 MCU 시간 |
| NetworkMs | 외부 클라이언트의 Write/ReadProperty 왕복 시간. 네트워크·클라이언트 처리를 포함 |
| GcSamples | 준비 후 및 매 10회 순회 후 강제 GC로 얻은 가용 힙 |

64개 Object_List는 비분할 APDU 제한을 고려해 count와 각 index로 조회합니다.
매 규모마다 3회 준비 순회 후 GC 명령까지 준비에 포함하고, 100회 전체 객체 SET→GET을 수행합니다.
각 매핑의 float 원시 비트와 bool 값을 모두 확인하고 GC 표본 기준 잔류 증가가 **0 B**인지 검사합니다.
준비 후에는 각 종류의 첫/중간/마지막 객체를 로컬 변경하고 모든 AV/BV를 조회하여 비대상 값 보존을 검사합니다.
변경한 AV에 잘못된 형식·Infinity 쓰기를 거절한 뒤에도 전체 값이 유지되어야 합니다.
별도 클라이언트를 만들어 새 UDP peer/invoke ID 공간에서도 마지막 로컬 값을 재조회합니다.
서버 매핑 시험이므로 다른 invoke ID의 응답을 받아 모델을 갱신하는 Client 매핑 시험은 아닙니다.
이는 128개 값 일괄 응답이나 ReadPropertyMultiple/COV 시험이 아닙니다.

계측값은 BACnet store 객체 수를 소비하지 않도록 별도 **UDP47809**에서 조회합니다.
`BNS1` + 명령 바이트(0=조회, 1=응답 뒤 GC 요청, 2/3/4=첫/중간/마지막 AV/BV 로컬 변경)를 보내면
`BNS1` + 빅엔디언 uint32 14개(60바이트)를 반환합니다.
배열 인덱스: 0=객체 수, 1=생성 전 가용 힙, 2=저장소 생성 후, 3=Device 생성 후, 4=벤치마크 후,
5=AV ms, 6=BV ms, 7=직접순회수, 8=예약, 9=Debugger.IsAttached,
10=GC 후 가용 힙, 11=GC 카운터, 12=예약, 13=0x600D입니다.
프로토콜·진단 도우미의 지역 변수 수명이 끝난 뒤 GC를 실행하고, 다음 요청에서 완료 카운터를 확인합니다.
운영용 진단 서비스가 아니라 전용 시험 앱의 부가 채널입니다.

`sizes.csv`, 각 규모의 `measurements.json`·생성 소스·이미지·배포/피어 로그,
샘플 피어와 최종 복원 로그를 출력 폴더에 보관합니다.
시간은 TickCount64 해상도(실물 약 10ms)의 제약을 받습니다.
네트워크 처리를 소켓·폴링으로 분리한 계측이므로 일반 샘플의 RTT와 동일하다고 간주하지 않습니다.
GC 후 잔류량은 힙 최대 사용량·할당 총량·스택·네이티브·Wi-Fi 메모리가 아니며
전원 차단 후 재부팅·수시간/수일 반복 시험 또는 BTL 인증을 대신하지 않습니다.
프로토콜 및 UDP 메시지 할당은 그대로 남아 있습니다.

## 실물 결과

`bin\bacnet-mapping-hardware-final`에서 샘플의 AV/BV 128회 왕복 시 비트 일치와 품질·오류·
Object_List를 포함한 822개 검증, 세 규모의 각 100회 순회를 완료했습니다.
보드의 디버거 연결은 없었으며 원래 Modbus 앱 자동 복원과 COM6 읽기까지 통과했습니다.

| 객체 수 (AV/BV) | 모델+잠금 객체+저장소 | Device 추가 | 계측 포함 앱 PE | 배포 이미지 |
|---|---|---|---|---|
| 8 (4/4) | 672 B | 192 B | 4,384 B | 87,012 B |
| 32 (16/16) | 2,400 B | 312 B | 6,120 B | 88,748 B |
| 64 (32/32) | 4,704 B | 456 B | 8,456 B | 91,084 B |

BACnet core PE는 4,952 B이며 이번 매핑 추가로 런타임 DLL/공개 API를 변경하지 않았습니다.
직접 호출은 AV의 가장 작은 음의 subnormal(0x80000001)과 BV true를 사용했습니다.

| 객체 수 | AV SET→Read 100회 순회 | BV SET→Read 100회 순회 | Read RTT 중앙값 | Write RTT 중앙값 |
|---|---|---|---|---|
| 8 | 210 ms / 400쌍 | 80 ms / 400쌍 | 7.09 ms | 6.68 ms |
| 32 | 860 ms / 1,600쌍 | 320 ms / 1,600쌍 | 7.11 ms | 6.68 ms |
| 64 | 1,740 ms / 3,200쌍 | 650 ms / 3,200쌍 | 7.21 ms | 6.80 ms |

준비 후 각 규모의 11개 GC 표본은 모두 동일했고, 최대 잔류 증가는 **0 B**였습니다.
측정 구간의 ReadProperty/WriteProperty 합계는 20,800건이며,
준비·발견·Object_List·GC 진단은 이 건수에서 제외합니다.
PC의 직접 AV/BV 정상 읽기·쓰기에서도 준비 후 추가 할당이 0 B였으므로
근거 없이 캐시·공유 가변 스냅샷을 추가하거나 정의 저장 방식을 재설계하지 않았습니다.
이는 전체 통신의 무할당이나 힙 최대 사용량·장기 안정성을 의미하지 않습니다.

진행 중 실패 기록도 유지합니다. `bin\bacnet-mapping-first`는 증분 빌드 후 배포 이미지
누락으로 장치 변경 전에 중단되어 실행기가 샘플을 Rebuild하도록 바꿨습니다.
`bin\bacnet-mapping-hardware-complete`는 Device가 Object_List 첫 항목이라는
시험 피어의 색인 가정을 수정하기 전 실패했고, 원래 앱을 복원했습니다.
`bin\bacnet-mapping-hardware-verified`는 샘플의 인덱스별 읽기 중 한 번의 통신 실패로 중단했고
원래 앱을 복원했습니다. 기한/재전송을 늘려 숨기지 않았으며, 단발 실패의 원인은
확정하지 못했습니다. 이후 전체 성공 실행과 이 실패 기록을 혼동하지 마십시오.

`bin\bacnet-mapping-hardware-repeat`에서는 샘플의 AV/BV 1,024회 왕복
(6,198개 검증) 및 8/32/64개 재배포 후 각각 100회 전체 순회를 다시 완료했습니다.
메모리 생성 전후 차이는 위 표와 같았고, 모든 규모의 11개 준비 후 GC 표본은
각 실행 내에서 동일했습니다. 두 전체 실행의 측정 Read/Write는 합계 41,600건입니다.
AV 직접 호출은 220/870/1,730ms, BV는 70/320/640ms로 첫 실행의 해상도/지터 범위였습니다.
재실행의 Read RTT 중앙값은 7.03/7.09/7.22ms, Write는 6.60/6.63/6.79ms였습니다.
재실행도 원래 Modbus 앱 복원과 COM6 읽기를 첫 복원 시도에 통과했습니다.
이 두 실행은 수시간 반복 시험이나 즉시 재시도 없이 모든 네트워크 상황에서 안정적으로 동작함을 보장하지 않습니다.

## 최신 견고성 재검증 (2026-10-29)

`bin\bacnet-mapping-hardware-20261029-111849`에서 BACnet 4.0.0 외부 클라이언트로
샘플 256회 왕복과 **8/32/64개 객체별 100회 전체 순회**를 완료했습니다.
각 규모의 로컬 첫/중간/마지막 변경 격리, 거절된 쓰기 후 값 보존과 새 peer 재조회를 통과했고,
준비 후 GC 보존 힙 증가는 각 0 B였습니다.
원래 Modbus 앱 복원·COM6 읽기도 성공했습니다. 위 과거 자원/시간 표와 최신 기능 재검증 기록은 구분합니다.
